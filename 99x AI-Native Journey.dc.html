01 / Context

The bottleneck moved. Our process didn't.

The first thing worth understanding is where the cost actually sits. Writing code stopped being the expensive part; deciding what to build, holding context across a growing product surface, and trusting what came back is where our teams spent their weeks. The general lesson: adding AI to an unchanged process does not remove a queue, it fills the same one faster. Three pressures made that visible for us.

03 / The model, explained

Copilots, autopilots, and the process that governs both.

Three axes have to move together — tools, process and people — and the distinction between the two kinds of tooling matters most. Copilots are pulled by an engineer, in the IDE, on demand. Autopilots are triggered by the delivery lifecycle itself. Process decides how either is allowed to be used; people decide whether any of it survives contact with real work.

04 / The agent loop

Six agents, one loop, a human at every gate.

The Intent Delivery Framework is not a rule pack that gets stamped into a repo — it is an agent protocol. Six agents each own one moment of delivery, and the useful distinction between them is who initiates: push agents drive a session end to end, pull agents ask you for artifacts and score them, and the ambient agent is simply what the assistant becomes once the master rule file is loaded. How the review agent works.

Every other agent produces work. This one only judges it — it never generates code or creates files unprompted. It also runs before adoption: point it at the tickets, pull requests and retro notes a team already has, and the gap report it returns becomes the brief for onboarding. That is the whole argument for having a pull agent at all.

05 / Observability

You cannot improve what you cannot see.

Once agents perform part of the work, the usual delivery signals stop describing reality. Story points and commit counts say nothing about which steps an agent ran, what they cost, or whether a human reviewed the result. 99x AI Hub is the observability platform we built to close that gap: every step of a delivery workflow reports who participated — human, agent, or both — with tokens, cost and model attached. It is the measurement layer underneath the loop in section 04.

Concept 01
Workflows & node activities
A workflow models your real process on a canvas. Each node declares the activities that produce work, and each activity carries an actor mode: human, agent, or human+agent. Modelling the process first is what makes the numbers comparable later.
Concept 02
Actors
Team-scoped participants — a named engineer, or a non-human system such as a review agent. Because both are first-class, usage rolls up by person and by agent, and the split between them becomes a trend you can watch.
Concept 03
Events & correlation ids
Each push creates an activity event keyed by a correlation id: one usage instance, one step inside a larger task. That key is what lets you reassemble the true cost of a feature from dozens of scattered model calls.
How the data gets in

Pipelines report usage themselves — nobody fills in a form. A node activity exposes a webhook URL with the secret embedded in the path, which suits providers that cannot set headers; pipelines that can send a team key or personal access token as a bearer header instead.

Activity webhooks accept arbitrary JSON, so an existing tool rarely needs changing: JSONPath mappings translate its payload into Hub fields, and inbound filters drop events you do not care about. The design principle worth stealing — make reporting cheaper than not reporting, or it will not happen.

A single event, annotated
{ "correlationId": "550e8400-e29b-…", "actors": ["alice@99x.io", "PR Review Agent"], "dimensions": { "tokens": 1200, "costUsd": 0.024, "model": "gpt-4.1" } }
Four facts per step: which task it belongs to, who took part, what it consumed, which model did it. Everything on the dashboards is an aggregation of this shape.
What it lets us answer
Cost
What a feature actually cost to deliver, model spend included — not estimated after the fact.
Participation
Which steps ran agent-only, which kept a human in the loop, and how that mix is shifting per squad.
Concentration
Where usage clusters — usually a handful of activities, which is where tuning pays for itself.
Auditability
An evidenced answer for clients and security reviews about how AI was used on their work.
The honest caveat: observability changes behaviour. Measure token spend alone and teams optimise for cheap prompts; we pair every usage view with delivery outcomes so the two are read together.  Read the AI Hub documentation →
